# Fase 21 — contratos de identidade antes das extrações

Base medida nesta etapa: `backend/server.js` com 11.991 linhas e `handleApi` com 4.313 (`node scripts/measure-modularization.mjs --summary`). O código é a autoridade para os contratos; esta tabela registra a ordem dos blocos no dispatcher, antes de alterar seu proprietário.

## Fronteira comum

`OPTIONS`, health, rate limit, seleção de transação/repositório, origem de mutações de cliente e leitura do snapshot ocorrem antes dos blocos abaixo. A origem das mutações autenticadas é conferida por `customerMutationOriginAllowed`; login/registro/reset com cabeçalhos de navegador também passam pela política. `adminOriginAllowed` rejeita `sec-fetch-site: cross-site`, permite hosts configurados e só aceita ausência de Origin/Referer fora da produção. O CORS e os cabeçalhos de segurança pertencem ao servidor. Nenhum handler pode usar ID de usuário vindo do corpo como identidade autenticada.

`cine_admin` é assinado, HttpOnly, Path=/, 8 horas por padrão; a sessão desktop usa `adminSessionMaxAge(req)`. `cine_customer` é assinado, HttpOnly, Path=/, 30 dias. Ambos usam SameSite=Lax, ou SameSite=None se os hosts frontend/backend de produção diferirem; Secure em produção. Os payloads incluem `sub`, `role`, `sv`, `exp`; Admin inclui `amr`. `getAdminUser` e `getCustomerUser` exigem conta ativa e `sessionVersion` igual. Logout e troca de senha revogam sessões antigas por incremento de versão. `cine_checkout` é limpo no logout de cliente. OAuth usa `cine_google_oauth`, HttpOnly, SameSite=Lax, escopo do app e 10 minutos.

`ensureAdmin` permanece no dispatcher, depois de login/logout/GET me e da métrica pública, antes do perfil/2FA e demais rotas Admin. Exige conta Admin ativa; responde 401 antes de 428 por configuração de 2FA; 428 antes de permissão 403; permissão antes de origem 403. As permissões são as de `adminPermissionService`, calculadas no backend, e `req.adminUser` só é atribuído após os guards. Os dois logins passam por bloqueio progressivo e limites por IP; os demais limites estão em `RATE_LIMIT_RULES`. Respostas de sucesso preservam o momento de escrita no repositório/JSON antes do cookie ou do `sendJson`.

| Pré-guard | `POST /api/admin/login/2fa` | Challenge inválido/expirado 401; TOTP ou código de recuperação, no máximo seis tentativas; sucesso 200 e cookie. Consumo de recovery code é condicional no repositório PostgreSQL ou em seção crítica JSON. | Script 2FA; replay HTTP incompleto. |

Limites globais relevantes: login cliente/Admin 12/min; challenge Admin 6/5 min; registro 10/h; reset 5/15 min (pedido) e 10/15 min (confirmação); verificação de e-mail 8/15 min e 2/min; troca de e-mail 5/15 min e 2/min; senha Admin 6/15 min; foto Admin 20/10 min; mutações Admin 180/min e cliente 120/min. O bloqueio progressivo de login é adicional. Não se deve mover esses controles para handlers nem reinicializar o estado de limites por request.

## Escopo seguro da etapa

`adminSessionRoutes` pode ocupar exatamente o slot pré-guard. `adminAccountRoutes` deve ocupar o primeiro slot pós-guard. `customerAuthRoutes` e `customerAccountRoutes` ocupam dois slots contíguos após as rotas de e-mail Admin. OAuth, exclusão de usuário e outras rotas de direitos ficam no dispatcher até testes dirigidos de callback, vínculos e falhas. Nenhum módulo inicializa worker, sessão ou conexão no import. Os testes JSON usam arquivo temporário; PostgreSQL só em banco descartável protegido.
