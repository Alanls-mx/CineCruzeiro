# Plano de modularização profunda

Base e medições em [MODULARIZATION_BASELINE.md](MODULARIZATION_BASELINE.md). Este plano define **hipóteses de extração**, não autorização para alterar finanças, autenticação ou provedores. Cada etapa será um commit independente na branch `codex/cine-modularizacao-profunda`, sem merge, migrations ou deploy automáticos. O código é a fonte definitiva quando divergir do mapa.

## Arquitetura de destino

`backend/server.js` deve ficar como **composition root**: ambiente/configuração por instalação, servidor HTTP/WS, contexto de request, ordem de guards, dispatcher curto, transação e startup/shutdown. Os handlers de domínio recebem dependências explícitas via factory, como os quatro handlers já extraídos; não importam `server.js`. O fluxo `src/app/api/[...path]/route.ts` → backend e `src/services/cinemaApi.ts` continua com os mesmos métodos, cookies, headers e respostas. Nenhuma marca, URL, credencial ou banco de um cinema será fixado em módulo compartilhado.

`backend/public/admin.js` deve ficar como composição do painel: `state` único, `API_BASE`, sessão/ACL, carregamento, navegação, `renderAll` e registro único dos controladores. Novos módulos seguem o contrato `window.CineAdminModules` e são carregados antes de `admin.js` em `admin.html`; recebem apenas estado e comandos necessários. O evento delegado permanece centralizado ou é entregue a um controlador por domínio, com um `bind` idempotente e `dispose` para timers/WS. Nenhum módulo recebe uma cópia independente de `state`.

**Limite de tamanho:** alvo de 250–500 linhas por novo módulo; acima de 600, dividir por subdomínio ou por fronteira de leitura/escrita antes do merge. Não acrescentar blocos a `socialStudioService.js` (1.133), `paymentService.js` (920) ou `postgresStore.js` (1.727) apenas para reduzir os arquivos principais. Testes de contrato e harness podem ser divididos por domínio, sem alterar o requisito de banco PostgreSQL descartável.

## Método de cada commit

1. Congelar uma família de rotas ou um fluxo de painel: método, caminho/regex, precedência, autenticação/papel/permissão, origem/CSRF, rate limit, entrada, status, headers/cookies, persistência, evento/auditoria, efeito externo e ordem de commit. Usar `--conditions` e `--routes`, depois conferir manualmente o código.
2. Adicionar somente o teste comportamental **faltante** para o risco real. Capturar HTTP/PG para resposta após commit e navegador para listeners, estado e modais. Testes PG usam `TEST_DATABASE_URL` com marca de descartável; mocks para provedores. Não testar em banco operacional.
3. Extrair uma responsabilidade coesa. Manter a posição de chamada no dispatcher, factory com dependências explícitas e o mesmo dono de transação. O handler retorna `handled` apenas após concluir a resposta. Não transportar uma closure gigante nem criar dependência cíclica.
4. Comparar respostas e efeitos: status, corpo, headers, cookies, auditoria, linhas persistidas, idempotência, eventos WS/SSE e limpeza de timers. Em finanças, verificar commit local antes de sucesso e não repetir chamada externa com identidade nova.
5. Atualizar `domains.md`, `modules.md`, `endpoints.md`, `flows.md`, `persistence.md`, `transactions.md` e `dependencies.md` **onde o dono realmente mudar**; registrar risco e testes. Rodar teste dirigido, `test:unit`, `test:security:local`, `lint`, `build`, `docs:check` e, quando necessário, E2E/PG descartável. Recontar linhas e tamanhos. Commit separado; parar em diferença de contrato.

Os critérios específicos abaixo se somam ao critério comum de equivalência. `Risco médio` ainda exige revisão de permissão e escritor; `financeiro crítico` requer failpoints antes/depois do commit, concorrência e idempotência. Uma extração que apenas mova linhas para outro arquivo de mil linhas não conta como progresso.

## Riscos transversais e condição de conclusão

- **HTTP/segurança:** centralizar a matriz método×rota×autorização antes de mover auth, uploads ou handlers financeiros. Preservar rate limit, origem, cookies, CORS, CSP, callback HMAC/token e ordem de dispatch.
- **Persistência:** conferir escritores em `persistence.md` e limites em `transactions.md`. `postgresStore.js` agrega snapshot, locks e pós-commit; não fazer refatoração paralela dele. JSON permanece apenas como compatibilidade nos testes próprios.
- **Efeitos externos:** Mercado Pago, PagBank, Point, SMTP, Wallet, CRM, Discord e Studio nunca entram no mesmo commit do PostgreSQL. Preservar chaves, leases, outbox, fencing, respostas de incerteza e retries; testes usam mocks e PG descartável.
- **Admin:** uma mudança em `admin.html` pode quebrar IDs, `data-*`, CSS, CSP ou ordem de scripts mesmo com API correta. Exigir E2E de painel e checagem de console para cada controlador novo.
- **Outros monólitos:** não deslocar dívida para `admin.css`, `social-studio.js`, `CheckoutPage.tsx` ou `smoke-tests.js`; acompanhar `--files` e abrir plano separado se crescerem.

O alvo de linhas é considerado atingido apenas com os dois intervalos pedidos **e** módulos de domínio legíveis, contratos preservados, testes dirigidos e gerais verdes, documentação de rotas/persistência atualizada e nenhuma lacuna financeira nova. Nenhum resultado local desta branch autoriza deploy.
